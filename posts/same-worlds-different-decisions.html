Same Worlds, Different Decisions

How to compare engineering decisions fairly in simulation.

August 2026 · Tsung-Yen Tsai

Suppose two policies run in simulation.

Policy A produces 120 reshuffles. Policy B produces 80.

It is tempting to say that B is better.

But that conclusion only makes sense if both policies were solving the same problem. If A started with a harder inventory distribution, or B happened to receive an easier picking sequence, then the result mixes two things together: the policy and the problem it happened to receive.

A fair comparison has to separate them.

I encountered this while building a discrete-event simulation for a high-density AS/RS system. In an earlier article, I wrote about how we chose the model around the decision we needed to make.

Once that model existed, a different question became important:

How do we know that a difference between two strategies actually came from the strategy?

Give every policy the same problem

One experiment compared three ways of organizing picking requests.

Normal ordering kept the generated request sequence. Merge ordering grouped requests for the same container while preserving each container's first appearance. Batch ordering grouped requests first by stack and then by the model's bottom-up access order.

For each seed and SKU occupancy level, every policy started with the same modeled inventory and the same raw picking requests. Only the request ordering changed.

The warehouse state affected which containers were blocked and how much reshuffling a request sequence could require. Holding the inventory and raw requests constant kept that source of variation out of the policy comparison.

If two strategies start from different problems, their outputs are not a fair comparison.

But making one comparison fair does not make one scenario representative.

Repeat the comparison across different problems

One warehouse state may happen to favor one strategy.

So the experiment repeated the same comparison across different seeded scenarios. At each tested SKU occupancy level, the three ordering strategies were compared across 30 seeded scenarios.

The scenarios changed between trials, but every policy faced the same scenario within a trial.

Testing only one scenario risks drawing a conclusion from a case that happens to favor one strategy. Giving each policy a different scenario creates the opposite problem: scenario difficulty becomes mixed into the comparison.

Instead, each scenario became one matched comparison, and the same comparison was repeated against different problems.

The point was not simply to get a better average. It was to ask whether the difference kept showing up after the problem changed.

One run shows that a result can happen. Repeated matched runs show whether the difference persists.

If it does, the next question is more useful than the final ranking:

What inside the system actually changed?

Do not stop at who won

In this AS/RS model, accessing a target container could require temporarily moving other containers that blocked it. We tracked those temporary relocations as reshuffle operations.

Request ordering mattered because it changed both which related requests were handled together and the order in which containers within a stack were accessed. In the simplified example above, accessing C2 before C1 requires C1 to be moved out of the way; batch ordering handles C1 first.

At each tested SKU occupancy level, batch ordering produced substantially fewer recorded reshuffles on average over the 30 seeded scenarios.

Inspecting the modeled execution helped explain why. By grouping related requests and aligning container access with the stack structure, batch ordering reduced accesses that required other containers to be temporarily moved out of the way.

That was more useful than a final ranking alone: the simulator exposed the difference and helped explain the mechanism behind it.

A useful simulation should show not only which policy performed better, but what changed inside the system when it did.

Sometimes, however, looking inside the decision reveals something else entirely.

Check whether the policy actually had a choice

In some highly constrained storage states, different reshuffle heuristics were left with the same feasible destination.

They had different preferences, but the system gave them the same action.

→ Location X

This was not the same as observing two algorithms with similar final scores.

They made the same choice.

That did not make the heuristics equivalent. When several feasible destinations existed, their preferences could still matter. But once the constraints reduced the feasible set to the same choice, there was no policy difference left to express.

This leads to a question that is easy to skip in optimization work:

Before asking which heuristic is better, is there anything meaningful left for it to choose?

A policy can only matter where the system leaves it a decision surface.

If the feasible set forces every tested strategy into the same action, improving the policy may have little system-level value. The more important lever may be the layout, capacity, constraints, or problem formulation.

Simulation can therefore answer something more useful than “which algorithm won?” It can show whether algorithm choice has leverage at all.

Know what the comparison can tell you

There is one final boundary around the experiment.

Outcome Model coverage What we could conclude
Reshuffle behavior Request ordering, container access, and reshuffle operations Compare how ordering policies changed reshuffles under the modeled storage mechanics
Production throughput Full robot routing, multi-robot traffic, and congestion were outside this experiment Could not determine how the policy would affect end-to-end field throughput

A policy that reduced reshuffling might also reduce traffic — or it might concentrate robot activity and create another bottleneck.

This experiment did not answer that question.

In the previous article, What Is Your Simulation Actually Testing?, I looked at the same evidence discipline through integration boundaries: which production behavior actually remained in the loop. Here, the question is inside the model: which mechanisms were represented for the outcome being compared.

If the model does not represent a mechanism, the experiment cannot tell us how that mechanism changes the comparison.

That does not make the result weak. It makes the result specific.

Comparing decisions, not just simulating systems

Looking back, the most reusable lesson was the comparison pattern:

  1. Give each strategy the same problem.
  2. Repeat the comparison across different problems.
  3. Look at what changed inside the system.
  4. Check whether the strategy actually had a meaningful choice.
  5. Be precise about what the model can actually compare.

That is when simulation becomes more than a representation of a system.

It becomes a practical way to compare engineering decisions.

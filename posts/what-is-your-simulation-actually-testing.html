What Is Your Simulation Actually Testing?

How integration boundaries shape what simulation results can support.

August 2026 · Tsung-Yen Tsai

In my last article, I argued that simulation fidelity should follow the question. You do not need to preserve every part of reality. You need the parts that matter to the decision.

Robotics adds another design choice: where should simulation connect to the production stack?

A simulated robot can still run the production navigation and localization code, with only the physical world and sensors replaced. Or robot-local execution can be replaced while the fleet-management software remains in the loop. The system can be simplified further by replacing most robot execution with a mock agent.

They are all simulations, but they are testing different parts of the system.

Keep production navigation in the loop, and navigation failures are part of the test. Replace it, and the test can no longer say much about the production navigation stack.

Deployment makes the boundary concrete

I encountered this problem during an AMR deployment in a manufacturing environment. We started with two robots, and actual throughput was well below the pre-deployment estimate.

There were plenty of things we could change: robot speed, routes, task sequencing, docking behavior, traffic settings, layout, and robot count.

Those changes could all be tested directly in the field, but that is an expensive way to experiment. Every change takes engineering time and carries deployment risk. The field is the final reality check, but it should not be the place to try every hypothesis.

We already had a Unity-based simulation connected to the FMS, so we used it to study the deployment before making changes in the field. For a fleet-throughput problem, the practical question was how much of the production robot stack needed to remain in the loop.

The simulation-backed deployment work eventually supported a throughput improvement of more than 40%.

Three boundaries, three systems under test

Looking back, I can group the configurations we used into three integration boundaries. This is a retrospective framing. They were not three equally mature modes designed as a formal architecture from day one.

Boundary Production code in the loop Substitute Primarily tests
Full-stack FMS + full robot stack World + sensors Robot stack + FMS integration
Partial-stack FMS task and traffic logic Robot-local execution FMS decisions + fleet flow
Mock-agent FMS interfaces + lifecycle Most robot execution FMS scalability + reliability

In the full-stack configuration, production navigation and localization actually ran. Unity provided the environment and generated simulated sensor feedback such as LiDAR point clouds. This was useful when navigation or FMS-to-robot integration was part of the question, because failures in those components remained visible.

For fleet-throughput experiments, production localization was not the behavior we needed to validate. Keeping the full robot stack in the loop added computational cost and introduced navigation and localization failure modes that were outside the fleet-level behavior we were trying to isolate.

We therefore used a simpler boundary for fleet-level experiments. The production FMS still handled task decisions and traffic logic, while robot-local planning, movement, and pose feedback came from a simulation-side implementation.

For FMS scale and long-running reliability, we simplified further. Lightweight agents in Unity accepted goals, moved through the simulated world, and reported state back to the FMS. This allowed us to exercise the system with more than 100 simulated AMRs and run multi-day 24/7 reliability testing.

These were not lower-quality versions of the same test. Each boundary preserved a different set of production behaviors. Full-stack simulation kept robot-local failures visible. Partial simulation focused on FMS decisions and fleet flow. Mock agents removed most robot execution so the FMS could be stressed at a much larger scale.

The integration boundary was part of the test design.

A second physical world exposes hidden contracts

Connecting a simulator to production software created another class of problem. The first issues were often not about physics. They were about state.

Unity needed to initialize racks and robots. The FMS also reconstructed its own view of the system. If those two initialization paths produced different states, both systems could start normally while reasoning about two different factories.

That forced a basic question: where does the initial state actually come from?

Robot state had the same issue. Position was only one field. The FMS also depended on carrying state, lift state, task state, agent state, and error state. These states affected what the system could assign next and how it interpreted an action in progress.

With one physical implementation, some assumptions can stay hidden in startup order, configuration, or timing. Add a second implementation and those assumptions have to become explicit. State ownership needs to be clear. Action completion needs a shared meaning. Both sides need to agree on which updates are authoritative.

I led the FMS-side integration, so part of my job was to trace those boundaries when something went wrong. Was the problem in the FMS, the robot logic, Unity, the communication layer, or simply the test setup? That diagnosis becomes difficult when the responsibilities between components are not clear.

Simulation integration therefore became an architecture test as much as a simulation task.

This does not mean every physical dependency should be easy to simulate. Some are difficult for good reasons. But when the responsibility boundary is reasonable, substituting a dependency forces us to make its interface, state ownership, and lifecycle much more explicit.

Evidence is claim-relative

A simulation does not have one global level of trustworthiness. What it can tell us depends first on which production code actually ran and which behavior was replaced.

A substitute can fail in both directions.

The FMS workflow was asynchronous. Routes and traffic information could change while robots were still executing tasks. Our partial agent preserved enough of that behavior to expose race conditions and state-ordering problems, but it was still not the production robot implementation.

A failure observed there was a reason to investigate the interaction across the boundary. It was not proof that a real robot would reproduce the same sequence.

The reverse is also possible. A mock that reduces the interaction to receive command → move → complete is convenient, but timing, lifecycle, or recovery behavior that matters in production can disappear from the test.

Preserving the contract made substitution possible. How well the substitute represented the relevant behavior determined which claims the result could support.

I think of the resulting limit as the evidence ceiling.

If production localization never ran, the test cannot support a claim about production localization. If most robot execution was replaced by mock agents, a reliability run with more than 100 simulated AMRs can provide useful evidence about FMS scalability and long-running behavior. It says very little about how 100 physical robots would navigate the same environment.

A partial simulation can show that a fleet-level change improves congestion or throughput under the behaviors represented by that simulation. That may be enough to decide that a change is worth testing in the field. It is not validation of the production navigation stack, because that stack was not part of the experiment.

What we simulate away places a hard limit on the claims the result can support.

Scenario coverage, calibration, observability, repeated runs, and evaluation still affect the strength of that evidence. They determine how close a test gets to the ceiling. But they cannot recover evidence for production behavior that was never in the loop.

Let the field test the boundary

The boundary still has to survive contact with the field.

In another deployment with very narrow paths, simulated robots could reach their expected locations with very little error. Real robots naturally had more positioning uncertainty.

Small localization and motion errors were enough to affect the FMS safety logic. In the real system, robot safety zones could overlap in situations that the simulation almost never produced.

One response would have been to add a better positioning-error model to simulation. But that was not the only option. The same field evidence could also mean that the deployed system needed to tolerate physical uncertainty more explicitly.

In practice, we adjusted waypoint placement, traffic buffers, and robot tolerances. The important point was not to reproduce every positioning error in simulation, but to account for the gap where it mattered in production behavior.

The sim-to-real gap did not automatically mean the simulator needed more detail. It showed that an uncertainty abstracted away below the simulation boundary could still affect the production software above it.

Sometimes that uncertainty should be modeled in simulation. Sometimes it should become part of the robustness contract of the production system. The field tells us whether the boundary kept the behavior that mattered.

At the integration boundary, I now check four things:

  • What production code actually ran?
  • What did we replace?
  • What failures can that substitute hide or create?
  • What claim are we trying to support?

Check the boundary before asking how realistic the simulation is.
